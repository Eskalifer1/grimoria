# TypeScript 7 as the checker, with Next.js driving the `tsc` CLI

The project runs **TypeScript 7** (`^7`, the native Go compiler), and `next.config.ts` sets `experimental.useTypeScriptCli: true`.

`tsconfig.json` turns on `strict`, plus `noUncheckedIndexedAccess` and `noImplicitOverride`. `strict` alone still lets `arr[0]` and `record[key]` claim to return a value that may not be there — which is precisely the shape of the code this app is made of: message catalogs keyed by locale and theme, and later Payload documents keyed by slug. `noImplicitOverride` costs nothing today, since there are no classes yet, and stops being free to add once there are. Both flags are independent of the version choice below; TypeScript 6 accepts them identically.

## Why the experimental flag is not optional

TypeScript 7 ships no public Compiler API. Next.js normally calls that API in a worker to type-check a build, so on `next@16.2.12` a plain TypeScript 7 install fails outright:

```
TypeScript 7.0.2 does not provide the compiler API required by Next.js.
Enable experimental.useTypeScriptCli in your Next.js config to use the
TypeScript CLI, or install TypeScript 6 instead.
```

That message names both exits, and Next ships the first one deliberately. TypeScript 7 support was backported into the `next-16-2` stable branch to fix a silent `SIGSEGV` crash on builds where TypeScript 7 was installed; 16.2.12 contains it. With the flag on, Next spawns `tsc` as a subprocess and reads its exit code — a supported route, not a workaround. The CLI runner has explicit handling for TypeScript 7's extensionless ESM bin and for the native compiler ignoring `SIGTERM`.

**Next 16.3.0 makes this the default** (`useTypeScriptCli: true` in its config schema), at which point the flag becomes redundant and gets deleted. That cleanup is #77.

## Why TypeScript 7 rather than staying on TypeScript 6

Measured on this repo — five cold runs each, same `tsconfig.json`, `--incremental false`:

| | Median |
| --- | --- |
| TypeScript 6.0.3 | 1.74s |
| TypeScript 7.0.2 | 0.28s |

Roughly **6.2× faster**, with both compilers reporting zero errors on the same strict config — the speed is not bought by checking less. Payload's own monorepo measured 5.46× on the same move, so this scales past a toy project.

TypeScript 6.0.3 is also the terminal 6.x release: it shipped 2026-04-16 and the `6.0.0-dev` nightly line stopped the same day. Staying there would mean parking on a closed branch to avoid one config line.

## What the missing Compiler API costs

**tsserver plugins do not work under TypeScript 7.** That includes the `{ "name": "next" }` entry in `tsconfig.json` and `@payloadcms/typescript-plugin` (which Payload disabled in its own repo on the same upgrade). Both are editor-only; neither affects build correctness.

This is survivable because the editor and the build no longer have to run the same TypeScript. VS Code type-checks with its own bundled TypeScript unless told otherwise, so the `next` plugin keeps working in the editor while `tsc` and `next build` use the workspace TypeScript 7. Pointing VS Code at the workspace version ("Use Workspace Version") does *not* work: `node_modules/typescript/lib/` contains `tsc.js` and no `tsserver.js` for the editor to launch. Editors that speak LSP directly can use `tsc --lsp --stdio`. TypeScript 7.1 is expected to ship a new API, which is when this constraint lifts.

**Nothing in the planned stack needs the Compiler API.** Checked package by package: `payload@3.87.0` has zero imports of the `typescript` package anywhere in its published `dist/`, and `generate:types` goes config → JSON Schema → `json-schema-to-typescript`. `@graphql-codegen/cli`, `vitest` and `@playwright/test` declare no dependency on it. `shadcn` does need it, through `ts-morph`, but `@ts-morph/common` vendors its own copy (`dist/typescript.js`, TypeScript 6.0.2) and never resolves the project's. typescript-eslint would be blocked, but Biome is the only linter here and has its own parser.

There is an official side-by-side package, `@typescript/typescript6`, which re-exports the TypeScript 6 API under a different specifier for tools that need it. Nothing here does, so it is not installed — noted only so the option isn't rediscovered.

**`baseUrl` is gone in TypeScript 7.** This config never used it; path mapping goes through `paths` alone.

## `yarn typecheck` runs `next typegen` first

`LayoutProps`, `PageProps` and the route union are generated by Next into `.next/types/`, so a bare `tsc --noEmit` fails on a fresh clone with `Cannot find name 'LayoutProps'`. The script is `next typegen && tsc --noEmit` so it stands alone — which is what CI (#42) needs, since it must not depend on a `next build` having run first.

## Verified, not assumed

On `typescript@7.0.2` and `next@16.2.12`, with both strict flags on: `yarn typecheck` passes from a clean tree, `yarn build` passes (TypeScript step ~0.5s), and `next start` renders both theme catalogs. Removing `useTypeScriptCli` reproduces the failure above, confirming the flag is load-bearing rather than decorative.

The lockfile carries all twenty of TypeScript 7's platform binaries, including `linux-x64`, so CI resolves one without extra configuration.

Payload's half is now **executed, and the argument held**: with `payload@3.87.1` installed (#30), `generate:types` and `generate:importmap` run clean under TypeScript 7, and `yarn typecheck` and `yarn build` pass on the result. The one TypeScript 7 follow-up left is the `useTypeScriptCli` flag (#77).
