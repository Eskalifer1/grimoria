# Layers and structure

Which layer code belongs to and what each may hold. Routes are `routing.md`; names are `naming.md`;
imports are `imports.md`. Where a rule is machine-enforced the config is named and is the source of
truth.

## Layers

Feature-Sliced Design, deliberately simplified — no `widgets`/`processes`, no `@x` notation, and no
FSD concept beyond what is here.

```
src/
  app/        Next.js App Router. Thin routing shell only.
  views/      Screen modules. Compose features into a full screen or shell.
  features/   Business features. Unique, not meant to be reused.
  entities/   Domain primitives needed by more than one feature.
  api/        Server data layer. Every call into Payload's Local API.
  shared/     Reusable code with no business-domain attachment.
```

Imports flow strictly downward: `app → views → features → entities → api → shared`. **Sideways is
forbidden on every layer** — feature from feature, entity from entity, screen module from screen
module. Machine-enforced (`style/noRestrictedImports`, scoped by path), so a violation is a design
signal rather than a lint error to route around. Two ways out:

- **One feature needs another's UI or behavior → compose in `views/`.** The feature does not import
  it; it accepts it as a `ReactNode`. Screen modules are the only place two features meet.
- **Two features need the same domain primitive → move it to `entities/`.**

**A check or step reaching a second call site moves down to the layer that owns it** — `entities/`
when it reads a domain shape, `shared/` when it does not. The second site is the trigger, not the
third.

### Files outside the layers

Framework-fixed — the framework or a generator dictates the path, layer rules do not apply, and any
layer may import them. **The list grows only by an explicit decision.**

| Path | Why |
| --- | --- |
| `src/proxy.ts` | Next.js resolves the request proxy here |
| `src/global.d.ts` | Ambient declarations (`next-intl` `AppConfig`) |
| `src/i18n/` | Default lookup path for `createNextIntlPlugin()` |
| `src/payload.config.ts`, `src/collections/` | Payload resolves its config here |
| `src/admin/` | Components Payload's admin renders, reached by string path through the import map |
| `src/constants/` | Every fixed value the app decides on, one file per subject (`routes.ts`, `action.ts`, `role.ts`, `theme.ts`, `user.ts`, `app.ts`) — any layer imports them, they import nothing |
| `src/payload-types.ts` | Generated by Payload — never hand-edited |
| `src/migrations/` | Generated by `payload migrate:create` — never hand-edited, excluded from Biome and cspell (`docs/database-migrations.md`) |
| `src/app/(payload)/` | Vendored from Payload's template — never hand-edited |
| `src/instrumentation.ts` | Next.js instrumentation hook (Sentry, #41) |
| `src/styles/` | Ours by choice: one token file per Theme, so a token added to one and forgotten in the other shows up in the changed-file list |

## `views/` — screen modules

The composition root for one rendered surface: **pages** (`NotesListPage`) and **shells**
(`AppShell`, `PublicShell` — `docs/features/site-layout.md`), both re-exported by an `app/` file.
**A shell lives here, never in `features/` or `shared/`.**

## Feature, entity, api and shared structure

- **`features/note/`, `entities/user/`** — `components/`, `hooks/`, `lib/`, `types.ts`.
- **`api/note/`** — one file per read or action, plus `api/core/` for the session, the permissions,
  the Payload client and `createAction`.
- **`shared/`** — `components/`, `components/ui/`, `hooks/`, `lib/`, `config/`, `types/`.

Create a segment when there is something to put in it; do not invent new segment names.

**A `"use server"` file is a security boundary.** Every export of one is a publicly reachable
endpoint callable with any arguments, so: one export per file, and it is an intended endpoint. Nothing
else may be exported — a schema or a type there breaks the module at runtime — so the contract gets
a sibling file. Helpers are imported, never written under the directive, and the
companion-helper allowance in `imports.md` never applies here.

### `api/` — the server data layer

**Every call into Payload's Local API lives here**, one folder per domain (`api/user/`,
`api/note/`), each file one read or one action. `api/` imports `shared/` and `src/constants/` and
nothing above it, and never another `api/` domain.

**`api/core/` is the exception every domain may import** — the Payload client, the session, the
permission helpers and the action wrapper, none of them domain-bound. It sits under `api/` rather
than in `shared/` because it touches Payload. Inside a domain, siblings are imported relatively;
`core/` is imported by alias. Machine-enforced (`style/noRestrictedImports`),
along with the fence that makes importing `payload` or `@payload-config` from any other layer a lint
error — the exempt trees are the Payload-owned ones listed in that override in `biome.json`.

**This departs from Feature-Sliced colocation deliberately** (#49): data access sits in one tree
rather than in an `api/` segment inside each feature, so there is one obvious place to look for
everything that touches the database and a backend swap touches one tree.

**`entities/` holds domain primitives** — the small UI more than one feature needs; its data comes
from `api/`. Three rules keep it from becoming a second `features/`: an entity appears only when a
**second real consumer** does, never speculatively; it holds **primitives only**, so anything that
decides rather than displays belongs to a feature; and there are **no cross-entity imports**.

**`shared/` has no business-domain attachment.** Promote a **component** only after a second real consumer exists and only if it
is genuinely domain-agnostic — if the second consumer needs it _because it shows domain data_, the
destination is `entities/`. A **generic function** (formatter, guard, pure helper) may go in on
first use; the test is "is this inherently generic?", not "might I copy-paste it someday?".

### `shared/components/ui/` — the vendored zone

Restructuring `ui/` breaks shadcn's CLI update path, so this one path is an explicit exception zone: files stay exactly as the CLI
writes them (kebab-case, multiple exports, no folder-plus-`index.tsx`) and fixes go upstream or
into a wrapper; the rule of two does not apply, so a primitive is installed the first time it is
needed; and everything we write ourselves, wrappers included, lives **outside** `ui/` under normal
rules.

`components.json` pins every alias, or the CLI writes into the wrong tree. `utils` points at
`shared/lib/cn.ts`, not a `lib/utils.ts` grab-bag.
