# i18n and copy conventions

Where catalogs live, how keys and namespaces are named, how a component reads a string, how
the two tonalities are written, how navigation inside the localized tree works. _Why_ the
system has this shape — two axes, full catalogs, copy resolved on the server — is
`docs/adr/0004-copy-system-locale-x-theme.md`. Settled rules, not options; where one is
machine-enforced the config is named, and that config is the source of truth.

## Adding a string: the whole loop

1. Pick the owning module → that is the namespace.
2. Add the key to `messages/en/standard.json`.
3. Write the dark-fantasy value for the same key in `messages/en/dark-fantasy.json`. Not
   later — `tsc` will not let you defer it.
4. Invented a term? Add it to the mapping table in the same change.
5. `yarn check:fix` — sorts both catalogs.
6. Read it in the component with `t`.

## The catalogs

```
messages/en/standard.json       client app, standard Theme
messages/en/dark-fantasy.json   client app, dark-fantasy Theme
messages/en/admin.json          /admin — no Theme at all
```

The client app is `locale × theme`: the active Theme selects **which catalog is loaded**,
never which key is read, so no component ever names a Theme (ADR-0004).

`/admin` is `locale` only — it sits outside `src/app/[locale]/` and is deliberately excluded
from theming (ADR-0001), so it has exactly one tonality. Its own catalog rather than a
namespace inside the theme catalogs, so that the client never ships admin copy, `/admin` never
ships client copy, and nobody writes dark-fantasy admin strings no user will ever see.

**Both theme catalogs are complete.** Dark-fantasy is not a sparse overlay: a new string is
written in **both** tonalities in the same change. Enforced — `src/i18n/messages.ts`
constrains every theme catalog to the key set of `standard`, so a forgotten key is a `tsc`
error naming the key, not standard copy leaking into the fantasy UI at runtime. Key names,
structure and nesting are identical across the two files; only the values differ.

**Key order is automatic.** Biome's `useSortedKeys` assist sorts `messages/**`;
`yarn check:fix` applies it, `yarn ci` fails on an unsorted file. Do not hand-order and do not
group by "importance" — the point is that the two theme catalogs read line-for-line against
each other.

## Keys

Short semantic keys, camelCase, at most three segments:

```
<namespace>.<element>[.<role>]

homePage.title
noteCard.readMore
noteForm.title.placeholder
```

The optional third segment is a **role** — `label`, `placeholder`, `aria`, `error` — added
only when one element genuinely owns more than one string. `noteCard.readMore` does not become
`noteCard.readMore.label` on the chance a tooltip might exist one day.

A key describes what the string _is_, not what it currently _says_: `emptyState`, not
`youHaveNoNotesYet`.

**Sentence-as-key is forbidden** (`t("Create a note")`). It couples the key to the English
copy, so editing the wording means touching every call site — and here it fails twice over,
since two catalogs hold two different sentences for the same key, so there is no sentence the
key could be.

## Namespaces

**A namespace is the module that owns the string** — the folder name from `general.md`,
camelCased:

```json
{
  "appShell": { "skipToContent": "Skip to content" },
  "homePage": { "title": "My notes" },
  "noteCard": { "readMore": "Read more" }
}
```

**Not by route.** A route is a URL, and copy does not belong to a URL: `NoteCard` renders on
the notes list _and_ on the public page, so a `notes` namespace would force it either to
duplicate its strings or to read them out of a page it knows nothing about. This is the same
reason a feature may not import another feature.

Renaming a component means renaming its namespace. That is intended — a namespace with no
module is dead copy, and it stands out.

**`common` is for the genuinely ownerless** — `save`, `cancel`, `back`, `appName`. The test is
not "used more than once", it is "belongs to nobody": a string used by two note screens
belongs to the note module. `common` is not a landing zone for strings whose owner is unclear;
an unclear owner is a question about where the component belongs, answered in `general.md`.

## Reading copy in a component

**`useTranslations` by default** — it works in Server and Client Components alike.
`getTranslations` (and `getFormatter`) is for contexts already async and without hooks:
`generateMetadata`, Server Actions, route handlers.

```tsx
const t = useTranslations('homePage');

export async function generateMetadata() {
  const t = await getTranslations('homePage');
  return { title: t('title') };
}
```

**A component reads its own namespace.** Never pass an already-translated string down as a
prop:

```tsx
<NoteCardHeader title={t('title')} />   // ✗ where does this text come from? Three files away.
<NoteCardHeader />                      // ✓ NoteCardHeader owns its copy and reads it
```

A screen module passing a whole `ReactNode` is composition, not copy threading — that
exception is unaffected.

**`shared/` never calls `t`.** It is defined by having no domain attachment, and copy is
always domain-bound: a `Button` reading `common.save` is no longer reusable, because the next
screen needs "Publish". `shared/` components receive their text as props or `children`;
`entities/`, `features/` and `views/` call `t` directly, at any depth.

```tsx
// features/note/components/NoteForm/index.tsx
const t = useTranslations('noteForm');
<Button>{t('save')}</Button>   // Button just renders what it was given
```

## Writing the message itself

**ICU for anything that varies.** Plurals and interpolation live inside the message, never in
the component:

```jsonc
"count": "{count, plural, =0 {No notes} one {# note} other {# notes}}"
```

```tsx
{count} {count === 1 ? 'note' : 'notes'}   // ✗ other languages have more plural forms than two
```

The same applies to `select` for a variant that changes the whole sentence. A conditional
picking between two `t()` calls is usually a `select` that was not written.

**`t.rich` for markup inside a sentence.** Never split a sentence into two keys to wrap the
middle of it — word order is not universal, and the fragments cannot be reordered by a
translator.

```jsonc
"terms": "Read the <link>terms</link> before publishing."
```

```tsx
t.rich('terms', { link: (chunks) => <Link href="/terms">{chunks}</Link> });
```

**Dates and numbers go through the formatter** — `useFormatter`, or `getFormatter` in async
contexts. Not `toLocaleString`, not `Intl.*` by hand, not a date library's own locale
handling; those scatter locale decisions across components, which is the retrofit ADR-0004
exists to avoid.

```tsx
const format = useFormatter();
format.dateTime(note.createdAt, { dateStyle: 'medium' });
```

**A translation is never an argument to another translation.** `t('deleteConfirm', { thing:
t('note') })` reads as a sentence in English and as nothing in particular anywhere else, and
breaks grammatical agreement in both tonalities. Write the full sentence as one message.

## What must come from a catalog

**Everything the user reads or hears**, explicitly including the strings easy to forget
because they never appear on a screenshot:

- `aria-label`, `alt`, `title`, `placeholder`, and visually-hidden text;
- page metadata from `generateMetadata` — `title`, `description`, OG copy;
- error messages, validation messages, empty states, confirmation dialogs.

Three deliberate exceptions, and an exception not on this list is a bug rather than a
judgement call: **Payload collection and field labels** (Payload's own config, not app UI);
**copy inside design mockups**; **developer-facing strings** — log messages, thrown `Error`
messages, test fixtures.

`style/noJsxLiterals` rejects visible text written straight into JSX
(`<button>Save</button>` fails `yarn check`; `<button>{t('save')}</button>` passes). It is off
in the vendored zones and test trees (`src/shared/components/ui/**`, `src/app/(payload)/**`,
`tests/**`, `e2e/**`) — the first two are generated source, and a test rendering literal text
is normal.

Its strict mode (`noStrings`) is deliberately **not** enabled: it treats every JSX attribute
string as copy and rejects `className="flex"`, `href="/notes"` and `type="submit"`, which no
allow-list can rescue. So the a11y attributes above are a **review item**, not machine-checked.
If they start slipping in practice, the ready answer is a Biome GritQL plugin matching a
string literal in `aria-label` / `alt` / `placeholder` / `title` and nothing else — not
written in advance.

## Writing dark-fantasy copy

`docs/features/dark-fantasy-theme.md` holds the **vocabulary** — the standard → dark-fantasy
mapping table. This is how to write a string the table does not cover.

**Flavor the lexicon, keep the sentence.** Take the theme's verbs and nouns (bind, inscribe,
spell, grimoire, sigil); keep the structure, the register and roughly the length of the
standard string, because it renders in the same layout.

| Standard | Dark fantasy |
| --- | --- |
| Create a note | Inscribe a spell |
| You haven't written anything down yet. | No spells are bound to your grimoire yet. |
| Saving failed. Try again. | The binding failed. Try again. |
| Deleted permanently. This can't be undone. | Unbound forever. It cannot be recalled. |

Both ways of missing that level: **too little** — "Saving failed. Try again." left unchanged,
which stops the second catalog being a re-skin; **too much** — "Alas, thy spell hath slipped
from the vellum; make thy attempt anew.", archaic grammar at double the length, and the user
is now reading a poem about their failure.

Seven rules:

1. **Meaning is untouchable.** Nothing added, nothing lost. The dark-fantasy string tells the
   user exactly what the standard one does.
2. **Use the table.** A mapped term is used as mapped, never as a synonym. A note is a
   _spell_, not a _scroll_, not an _incantation_.
3. **Keep the shape.** Same sentence structure, same number of sentences, length within
   roughly ±20%.
4. **Register is solemn, not archaic.** No `thee`, `thou`, `hath`, no `Alas`. It reads as
   written by someone serious, not as costume.
5. **Errors and warnings are flavored, but the consequence stays literal.** The image may
   change; what happened and what it costs may not. ✓ "Unbound forever. It cannot be
   recalled." ✗ "The spell returns to the void." — nothing there says the data is gone.
6. **Data is never flavored.** Numbers, dates, user names, note titles, file names.
7. **A new term goes in the table**, in the same change. Otherwise the next string invents a
   second word for the same thing.

## Navigation and loading

**Navigation inside the localized tree goes through `src/i18n/navigation.ts`** — its `Link`,
`redirect`, `usePathname`, `useRouter`, `getPathname`. Importing `next/link` or
`next/navigation` there drops the active locale.

```tsx
import { Link } from '@/i18n/navigation';   // ✓
import Link from 'next/link';               // ✗ inside src/app/[locale]/**
```

Outside the localized tree — `/admin`, anything under `(payload)` — plain `next/*` navigation
is correct, because there is no locale segment to carry.

| Tree | Catalog loaded by |
| --- | --- |
| `src/app/[locale]/**` | `src/i18n/request.ts` — picks `messages/<locale>/<theme>.json` |
| `/admin` | the admin layout, supplying `messages/<locale>/admin.json` |

Which Theme is active is decided in exactly one place, `src/i18n/theme.ts`. How that choice is
stored, and why a Theme toggle must round-trip to the server, are
`docs/features/dark-fantasy-theme.md` and ADR-0004.

### The admin catalog

`/admin` is outside `src/app/[locale]/`, so `src/i18n/request.ts` does not serve it and its
layout supplies the catalog itself. Nothing about theme resolution applies there.

**Locale.** No locale URL segment and one locale in v1, so it uses `routing.defaultLocale`.
When user profiles exist (#32) it reads the user's locale — one branch in one place, the shape
`src/i18n/theme.ts` already uses for Theme.

**Typed keys.** next-intl binds `useTranslations` to a single global `Messages` type
(`src/global.d.ts`), which cannot be swapped per route tree, so `Messages` is the union of
both key sets and admin keys are checked by `tsc` like any other. The cost is accepted: admin
keys autocomplete in client components too, and writing one there fails visibly on first
render, because the client tree never loads that catalog.

Settled but not yet built — the catalog and the type land with the custom admin route (#37).
