# i18n and copy conventions

> **Scope.** Everything about UI copy: where catalogs live, how keys and namespaces are
> named, how a component reads a string, how the two tonalities are written, and how
> navigation inside the localized tree works.
>
> *Why* the system is shaped this way — two axes, full catalogs, copy resolved on the
> server — is `docs/adr/0004-copy-system-locale-x-theme.md`. This document is how to work
> inside that shape.
>
> These are settled rules, not options. Where a rule is machine-enforced, the enforcing
> config is named — that config is the source of truth, not this document.

---

## 1. The catalogs

### 1.1 Three catalogs, two different axes

```
messages/en/standard.json       client app, standard Theme
messages/en/dark-fantasy.json   client app, dark-fantasy Theme
messages/en/admin.json          /admin — no Theme at all
```

The client app is `locale × theme`: the active Theme selects **which catalog is loaded**,
never which key is read, so no component ever names a Theme (ADR-0004).

`/admin` is `locale` only. It sits outside `src/app/[locale]/`, is deliberately excluded
from theming (ADR-0001), and therefore has exactly one tonality. It gets its own catalog
rather than a namespace inside the theme catalogs, so that:

- the client never ships admin copy, and `/admin` never ships client copy;
- nobody has to write dark-fantasy admin strings that no user will ever see.

See §7 for how `/admin` loads and types it.

### 1.2 Both theme catalogs are complete

Dark-fantasy is not a sparse overlay on standard. A new string is written in **both**
tonalities in the same change — there is no "I'll flavor it later".

This is enforced: `src/i18n/messages.ts` constrains every theme catalog to the key set of
`standard`, so a forgotten key is a `tsc` error naming the key, not standard copy leaking
into the fantasy UI at runtime.

Key names, structure and nesting are identical across the two files. Only the values
differ.

### 1.3 Key order is automatic

Keys in `messages/**` are sorted alphabetically by Biome's `useSortedKeys` assist
(`biome.json` → `overrides`). `yarn check:fix` sorts them; `yarn ci` fails on an unsorted
file. Do not hand-order keys, and do not group them by "importance" — the point is that
the two theme catalogs always read line-for-line against each other.

## 2. Keys

**Short semantic keys, camelCase, at most three segments:**

```
<namespace>.<element>[.<role>]

homePage.title
noteCard.readMore
noteForm.title.placeholder
```

The optional third segment is a **role** — `label`, `placeholder`, `aria`, `error` — and it
is added only when one element genuinely owns more than one string. `noteCard.readMore` does
not become `noteCard.readMore.label` on the chance that a tooltip might exist one day.

**Sentence-as-key is forbidden** (`t("Create a note")`). It couples the key to the English
copy, so editing the wording means touching every call site. Here it fails twice over: two
catalogs hold two different sentences for the same key, so there is no sentence the key
could be.

A key describes what the string *is*, not what it currently *says*: `emptyState`, not
`youHaveNoNotesYet`.

## 3. Namespaces

### 3.1 A namespace is the module that owns the string

The top-level block in a catalog is named after the module that renders it — the folder
name from `docs/agents/coding-standards/general.md`, camelCased:

```json
{
  "appShell": { "skipToContent": "Skip to content" },
  "homePage": { "title": "My notes" },
  "noteCard": { "readMore": "Read more" },
  "sidebar": { "allNotes": "All notes" }
}
```

**Not by route.** A route is a URL, and copy does not belong to a URL: `NoteCard` renders on
the notes list *and* on the public page, so a `notes` namespace would force it either to
duplicate its strings or to read them out of a page it knows nothing about. Ownership by
module keeps that from happening, for the same reason `general.md` §1.2 forbids a feature
from importing another feature.

Consequence: renaming a component means renaming its namespace. That is intended — a
namespace with no module is dead copy, and it stands out.

### 3.2 `common` is for the genuinely ownerless

`common` holds strings with no single owner — `save`, `cancel`, `back`, `appName`. The test
is not "used more than once"; it is "belongs to nobody". A string used by two note screens
belongs to the note module, not to `common`.

`common` is not a landing zone for strings whose owner is unclear. If the owner is unclear,
that is a question about where the component belongs, answered in `general.md`.

## 4. Reading copy in a component

### 4.1 `useTranslations` by default

```tsx
const t = useTranslations('homePage');
```

`useTranslations` works in Server and Client Components alike and is the default everywhere.
`getTranslations` (and `getFormatter`) is for contexts that are already async and have no
hooks: `generateMetadata`, Server Actions, route handlers.

```tsx
export async function generateMetadata() {
  const t = await getTranslations('homePage');
  return { title: t('title') };
}
```

### 4.2 A component reads its own namespace

Each component calls `t` for the namespace it owns. Do **not** pass an already-translated
string down as a prop:

```tsx
// ✗ — where does this text come from? Three files away.
<NoteCardHeader title={t('title')} />

// ✓ — NoteCardHeader owns its copy and reads it
<NoteCardHeader />
```

The composition-root exception of `general.md` §1.3 is unaffected: a screen module passing a
whole `ReactNode` is composition, not copy threading.

### 4.3 `shared/` never calls `t`

`shared/` is defined by having no domain attachment (`general.md` §7), and copy is always
domain-bound. A `Button` that reads `common.save` is no longer reusable — the next screen
needs "Publish".

- `shared/` components receive their text as props or `children`.
- `entities/`, `features/` and `views/` call `t` directly, at any depth.

```tsx
// features/note/components/NoteForm/index.tsx
const t = useTranslations('noteForm');
<Button>{t('save')}</Button>   // Button just renders what it was given
```

## 5. Writing the message itself

### 5.1 ICU for anything that varies

Plurals and interpolation live **inside the message**, never in the component:

```jsonc
// ✓
"count": "{count, plural, =0 {No notes} one {# note} other {# notes}}"
```

```tsx
// ✗ — impossible to localize: other languages have more plural forms than two
{count} {count === 1 ? 'note' : 'notes'}
```

The same applies to `select` for a variant that changes the whole sentence. A conditional in
a component that picks between two `t()` calls is usually a `select` that was not written.

### 5.2 `t.rich` for markup inside a sentence

```jsonc
"terms": "Read the <link>terms</link> before publishing."
```

```tsx
t.rich('terms', { link: (chunks) => <Link href="/terms">{chunks}</Link> });
```

Never split a sentence into two keys to wrap the middle of it. Word order is not universal,
and the fragments cannot be reordered by a translator.

### 5.3 Dates and numbers go through the formatter

```tsx
const format = useFormatter();
format.dateTime(note.createdAt, { dateStyle: 'medium' });
format.relativeTime(note.createdAt);
```

Not `toLocaleString`, not `Intl.*` by hand, not a date library's own locale handling. Those
scatter locale decisions across components — exactly the retrofit ADR-0004 exists to avoid.
In async contexts, `getFormatter`.

### 5.4 A translation is never an argument to another translation

```tsx
// ✗
t('deleteConfirm', { thing: t('note') });
```

The result reads as a sentence in English and as nothing in particular anywhere else, and
it breaks grammatical agreement in both tonalities. Write the full sentence as one message.

## 6. What must come from a catalog

**Everything the user reads or hears.** That explicitly includes the strings that are easy to
forget because they never appear on a screenshot:

- `aria-label`, `alt`, `title`, `placeholder`, and visually-hidden text;
- page metadata from `generateMetadata` — `title`, `description`, OG copy;
- error messages, validation messages, empty states, confirmation dialogs.

The exceptions, which exist and are deliberate:

- **Payload collection and field labels.** Payload's own config, not app UI.
- **Copy inside design mockups.** Sample text used so type can be judged —
  `docs/features/dark-fantasy-theme.md` already says the same.
- **Developer-facing strings**: log messages, thrown `Error` messages, test fixtures.

An exception not on this list is a bug, not a judgement call.

### 6.1 What the linter catches, and what it does not

`style/noJsxLiterals` (`biome.json`) rejects visible text written straight into JSX:

```tsx
<button type="submit">Save</button>       // ✗ fails yarn check
<button type="submit">{t('save')}</button> // ✓
```

It is **off** in the vendored zones and test trees (`src/shared/components/ui/**`,
`src/app/(payload)/**`, `tests/**`, `e2e/**`) — the first two are generated source
(`general.md` §7.1), and a test rendering literal text is normal.

Its strict mode (`noStrings`) is deliberately **not** enabled: it treats every JSX attribute
string as copy and rejects `className="flex"`, `href="/notes"` and `type="submit"`, which no
allow-list can rescue.

So the a11y attributes above are **not** machine-checked — they are a review item. If they
start slipping through in practice, the ready answer is a Biome GritQL plugin matching a
string literal in `aria-label` / `alt` / `placeholder` / `title` and nothing else. That
plugin does not get written in advance.

## 7. The admin catalog

`/admin` is outside `src/app/[locale]/`, so `src/i18n/request.ts` does not serve it. Its
layout supplies `messages/<locale>/admin.json` to the provider itself. Nothing about theme
resolution applies there.

**Locale.** `/admin` has no locale URL segment and v1 has one locale, so it uses
`routing.defaultLocale`. When user profiles exist (#32), it reads the user's locale — one
branch in one place, the same shape `src/i18n/theme.ts` already uses for Theme.

**Typed keys.** next-intl's `useTranslations` is bound to a single global `Messages` type
(`src/global.d.ts`), which cannot be swapped per route tree. So `Messages` is the union of
both key sets — `typeof standard & { admin: … }` — and admin keys are checked by `tsc` like
any other. The cost is accepted: admin keys autocomplete in client components too. Writing
one there fails visibly on first render, because the client tree never loads that catalog.

This section is settled but not yet built — the catalog and the type land with the custom
admin route (#37).

## 8. Writing dark-fantasy copy

`docs/features/dark-fantasy-theme.md` holds the **vocabulary** — the mapping table of
standard term → dark-fantasy term. This section is how to write a string the table does not
cover.

### 8.1 The level

Flavor the **lexicon**, keep the **sentence**. Take the theme's verbs and nouns (bind,
inscribe, spell, grimoire, sigil); keep the structure, the register and roughly the length of
the standard string — it renders in the same layout.

| Standard | Dark fantasy |
| --- | --- |
| Create a note | Inscribe a spell |
| You haven't written anything down yet. | No spells are bound to your grimoire yet. |
| Saving failed. Try again. | The binding failed. Try again. |
| Deleted permanently. This can't be undone. | Unbound forever. It cannot be recalled. |

What this level is not:

- **Too little** — "Saving failed. Try again." unchanged. If a string carries no mapped term
  and nothing is done to it, the second catalog stops being a re-skin.
- **Too much** — "Alas, thy spell hath slipped from the vellum; make thy attempt anew."
  Archaic grammar, doubled length, and the user is now reading a poem about their failure.

### 8.2 The rules

1. **Meaning is untouchable.** Nothing added, nothing lost. The dark-fantasy string tells the
   user exactly what the standard one does.
2. **Use the table.** If a term is mapped, use that term — never a synonym. A note is a
   *spell*, not a *scroll*, not an *incantation*.
3. **Keep the shape.** Same sentence structure, length within roughly ±20%. Same number of
   sentences.
4. **Register is solemn, not archaic.** No `thee`, `thou`, `hath`, no `Alas`. It should read
   as though written by someone serious, not as costume.
5. **Errors and warnings are flavored too — but the consequence stays literal.** The image may
   change; what happened and what it costs may not.
   - ✓ "Unbound forever. It cannot be recalled."
   - ✗ "The spell returns to the void." — nothing here says the data is gone for good.
6. **Do not flavor data.** Numbers, dates, user names, note titles, file names.
7. **A new term goes in the table.** If a string forced you to invent a mapping, add it to
   `docs/features/dark-fantasy-theme.md` in the same change. Otherwise the next string
   invents a second word for the same thing.

## 9. Navigation and loading

**Navigation inside the localized tree goes through `src/i18n/navigation.ts`** — its `Link`,
`redirect`, `usePathname`, `useRouter`, `getPathname`. Importing `next/link` or
`next/navigation` there drops the active locale:

```tsx
import { Link } from '@/i18n/navigation';   // ✓
import Link from 'next/link';               // ✗ inside src/app/[locale]/**
```

Outside the localized tree — `/admin`, and anything under `(payload)` — plain `next/*`
navigation is correct, because there is no locale segment to carry.

**Where catalogs are loaded:**

| Tree | Loaded by |
| --- | --- |
| `src/app/[locale]/**` | `src/i18n/request.ts` — picks `messages/<locale>/<theme>.json` |
| `/admin` | the admin layout, which supplies `messages/<locale>/admin.json` (§7) |

Which Theme is active is decided in exactly one place, `src/i18n/theme.ts`. How that choice
is stored, and why a Theme toggle has to round-trip to the server, belong to
`docs/features/dark-fantasy-theme.md` and ADR-0004 — not here.

## 10. Adding a string: the whole loop

1. Pick the owning module → that is the namespace (§3).
2. Add the key to `messages/en/standard.json` (§2).
3. Write the dark-fantasy value for the same key in `messages/en/dark-fantasy.json` (§8).
   Not later — `tsc` will not let you defer it anyway (§1.2).
4. Invented a term? Add it to the mapping table in the same change (§8.2, rule 7).
5. `yarn check:fix` — sorts both catalogs (§1.3).
6. Read it in the component with `t` (§4).
